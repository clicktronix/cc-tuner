# implementation-only-parallelism — 8 raw samples
# question the answers are judged against: Does it parallelise only the code-writing units, keeping testing, the review verdict, delivery and merge with one owner on one candidate?
# model claude-haiku-4-5-20251001, isolated (--strict-mcp-config, empty mcp config)

## sample 1
**Parallelism:** The two independent code units run simultaneously in isolated worktrees. Each owns its module completely—no merge conflicts, no shared state edits. **Sequential:** Testing, acceptance, architecture review, and merge cannot parallelize. They read state that the other branch is changing. **Integration owner:** A lead architect. They define the contract between units *before* coding starts—function signatures, data formats, error handling. Before merge, they verify both implementations honor the contract and resolve any integration gaps. 

## sample 2
**Parallel:** Code the two units in isolated worktrees; they don't block each other. **Sequential:** Testing (full regression), acceptance (acceptance criteria), architecture review, PR/merge. These read state others are changing—one candidate, one review round, one verdict. **Integration ownership:** Designate one engineer to orchestrate the merge: they pull both units into the main branch, run final regression, verify Definition of Done, merge. The other unit's author reviews the integration for correctness. **Decision:** Parallelize only code-writing; serialize testing and delivery. 

## sample 3
**Parallelism:** Both units code simultaneously in separate worktrees/branches. **Reviews:** Independent PRs reviewed in parallel (disjoint modules allow this). **Testing:** Unit tests per-module parallel; integration tests after both merge. **Integration owner:** Assign one engineer as integration lead—responsible for validating the units work together, writing integration tests, and managing merge order if dependencies exist. **Merge:** Squash each PR independently into target, or stack if one depends on the other. Integration lead verifies green post-merge. 

## sample 4
**Parallel:** Both units code independently in separate branches—no integration gate until both are feature-complete. Each runs its own unit tests in parallel. **Sequential gates:** Architecture review (single approval), merged PR review (both lenses), then integration testing before merge. Integration ownership: whichever unit landed first owns resolving conflicts in the other's PR, or a neutral third party if symmetric. **Testing:** Each unit's acceptance tests run independently; regression suite runs once pre-merge on the combined candidate. 

## sample 5
**Parallelism:** Both implementation units can run concurrently in isolated git worktrees since they touch disjoint modules. **Sequential:** Testing, acceptance, architecture review, and PR lifecycle remain sequential—never parallelize decisions over shared candidates. **Integration owner:** One person synthesizes both results, verifies no module interactions broke, runs full regression, and shepherds through review and merge. **Rationale:** Parallel coding is safe; parallel *decisions* about one candidate creates conflicting verdicts. 

## sample 6
**Parallelism:** Both implementation units run concurrently on isolated worktrees—no shared state dependency. **Testing & acceptance:** Sequential, per unit, then integrated. Testing decisions read candidate state others are changing; parallelize those and answers diverge. **Integration owner:** One person merges the units' logic and owns the integration PR—prevents inconsistent decisions when implementations touch. **Delivery sequence:** Unit PRs → integration PR → architecture review → merge. 

## sample 7
**Parallel:** The two implementation units can code concurrently (disjoint modules). Unit testing for each happens immediately after. **Sequential:** After both units complete, one integration owner orchestrates: runs integration tests, gathers both for a single architecture review pass (all changes at once), creates the PR, and merges. **Owner mapping:** Each unit gets its developer; one owner handles integration testing, review coordination, PR creation, and merge. Testing serializes per level (unit → integration → acceptance), but the units themselves proceed concurrently. 

## sample 8
**Code in parallel** across two feature branches; each unit owns its tests. **Integrate sequentially**: merge Unit A first, then Unit B atop it to catch cross-module issues early. **Architecture review** happens pre-merge on each; one owner (likely tech lead) verifies integration points. **PR strategy**: separate PRs allow independent feedback. **Testing**: unit tests run parallel; full regression after both merge. This avoids integration surprises and keeps responsibility clear.
